# Agent 主页「全量时间线往下滑」不符监控操作习惯：主屏只留最新一轮，setup 与长日志收进子页面 Dialog

## S · 背景（Situation）

- **项目 / 模块**：tansuo_agent Web 前端（`web/src/`，React + shadcn/ui）；紧接 STAR #028（同日）——028 刚把 Agent 页做成默认首页、按唤醒轮次渲染全量叙事时间线
- **环境**：同 #028；Windows 11，Node 20 + Vite 8 + TypeScript
- **当时在做什么**：028 提交后向用户确认效果，用户反问「你觉得当前 agent 界面就一轮一轮往下滑合适吗，符合用户操作吗」，随后明确反馈：「你现在好几个东西混在一个界面了，而且还有特别长的日志那个，不应该折叠进子页面吗，只在这个界面显示最新的就行」
- **问题表现**：028 版 Agent 主页的三个操作错位：
  1. **最新轮在页面最底部**——用户最高频动作是「看 agent 刚才干了什么」，每次打开都要滑到底；运行中 8s 轮询不断追加新轮，阅读位置持续漂移；
  2. **一屏混了多件事**——setup 控件区、setup 实时日志（`<pre>` 长文本）、setup 时间线、监督会话统计与全量时间线全在同一页纵向堆叠；
  3. **setup（一生一次的操作）永远占首屏**，真正持续演化的监督会话被压在下面。
- **影响范围**：不阻塞功能，但默认首页信息密度与动线错误——监控场景被做成了「档案馆」形态
- **复现步骤**：打开 :8000 默认 Agent 页 → 首屏是 setup 控件与说明 → 监督历史要往下滑，最新一轮在最底下

## T · 目标（Task）

- **要达成什么**：Agent 主屏只回答一个问题——「agent 现在/刚才在干什么」：只展示最新一轮监督卡片；完整历史与 setup（控件+长日志+setup 时间线）收进子页面
- **验收标准**：主屏无长日志、无 setup 控件；最新轮直达首屏；子页面打开即轮询、关闭即停；`npm run build` 通过；e2e_web_smoke 133 项全绿；后端零改动
- **约束条件**：项目无路由库（单页 Tabs 架构），不为此引入 react-router；复用既有 Dialog 组件（项目已有「Dialog 当子页面」先例：TutorialDialog）；不新增依赖

## A · 解决方案（Action）

### 排查过程

1. 先自查 028 版与真实使用场景的错配：监控类界面的主诉求是「瞥一眼最新状态」，高频动作是 glance（扫视）不是 browse（浏览）。全量正序时间线是档案馆/feed 形态，适合回溯不适合监控。
2. 向用户确认改进方向（AskUserQuestion 给了四个选项：最新在上+折叠 / 正序+自动跟随 / 左列表右详情 / 保持现状），用户的选择超出选项：**问题不在排列，在混装**——多件事应拆子页面，主屏只留最新。
3. 「子页面」的落地形式权衡：项目是 Tabs 单页架构无 router，引 react-router 成本高且与既有范式冲突；已有 TutorialDialog 用全屏 Dialog 承载整块内容（markdown 教程）的先例——沿用 Dialog 即「子页面」，关闭即卸载、轮询自动停止（`usePolling` 在组件卸载时清理 timer）。

### 尝试过的方案（含失败的）

| 方案 | 结果 | 失败/放弃原因 |
|------|------|--------------|
| 最新在上 + 旧轮折叠（原推荐选项） | 放弃 | 用户反馈核心是「混装」而非「排列」；折叠仍把所有轮次堆在主屏 |
| 正序 + 自动滚动跟随最新（聊天式） | 放弃 | 同上，且自动滚动对「回来查历史」的场景不友好 |
| 引入 react-router 做真实子页面路由 | 放弃 | 项目 Tabs 单页架构，为两个子视图引路由库成本不匹配 |
| Dialog 子页面（TutorialDialog 范式） | 采用 | 零新依赖；开合即挂载/卸载，轮询天然随动；既有先例一致 |

### 最终方案

1. **新 `web/src/components/SetupDialog.tsx`**：把 `SetupPanel`（控件 + 训练脚本选择 + 实时日志 + setup 时间线）整体包进全屏 Dialog（`max-h-[90vh] w-[min(96vw,64rem)]`，内容区 `overflow-y-auto`）。关闭即卸载 SetupPanel，其内部 3 个轮询（status/log/events）随之停止。
2. **新 `web/src/components/HistoryDialog.tsx`**：完整监督历史子页面——轮询 `agentEvents(cohort)` 8s，`groupByRounds` 后**反转**（最新在前）渲染 AgentTimeline，顶部统计行（轮数/累计 tokens）。
3. **重写 `web/src/pages/AgentPage.tsx`**：主屏只剩四块——
   - 操作条：[配置 agent（setup）] + [完整监督历史（N 轮）] + 累计 tokens；
   - setup 进行中提示条（若 running：徽章 + 「查看进度与日志」按钮——主屏不展示日志本体）；
   - **最新监督轮次**：`segments[segments.length - 1]` 单段渲染 AgentTimeline；
   - 空态卡（无监督记录时：说明 + 「先去配置 agent」CTA）。
   - 两个 Dialog 挂载在页尾，状态 `setupOpen/historyOpen` 控制。
4. `SetupPanel.tsx` 本体不动（原样被 Dialog 包裹复用）；`App.tsx` 不动（默认页与胶囊维持 028 成果）。

## R · 实际效果（Result）

- **验证方式**：`cd web && npm run build`（tsc -b）通过；`python tests/e2e_web_smoke.py` 133 项全绿（纯前端改动，端点未变）
- **前后对比**：主屏从「setup 控件 + 长日志 + 两条时间线纵向堆叠、最新在底部」变为「首屏一张最新轮卡片 + 两个子页面入口」；长日志只在打开 setup 子页面时可见且轮询随开合启停
- **副作用与代价**：查看历史多一次点击（打开 Dialog）——监控场景下这是正确代价（glance 路径变短，browse 路径多一步但目标明确）；Dialog 内滚动独立于页面滚动，无嵌套滚动问题（内容区单滚动容器）
- **遗留问题与后续**：无。若轮次极多（>50），历史子页面可再加分页/虚拟滚动，本期不做
- **经验教训**：
  1. **「叙事完整」不等于「操作友好」**——028 把每轮「看到/判断/做了」讲对了，但忽略了监控界面的主诉求是一次 glance 看到最新，不是从头读档案。做监控类视图先问「用户最高频动作是什么、需要滑几屏完成」；
  2. **设计验证要趁热问用户**——028 提交后一句「符合用户操作吗」的直接追问立即暴露了错位，比攒一堆功能再返工便宜得多；
  3. **AskUserQuestion 的选项可能框不住真实诉求**——四个排列方案之外，用户真正要的是「拆分」；选项要允许并认真对待 Other 回答里的方向性修正；
  4. **无路由单页架构里，全屏 Dialog 就是子页面**——开合即挂载/卸载的特性让轮询生命周期管理免费获得，比手动 paused 标志干净。
